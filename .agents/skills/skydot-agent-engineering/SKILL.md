# SkyDot Agent 工程协作

让一次交付满足用户目的，让下一次交付少重复同样的错误。按当前任务选择下面的工作方式，不为小改动附加完整流程。

## 项目上下文与执行边界

- 先阅读 [工程协作指南](../../../CLAUDE.md) 及相关模块的真相源；界面任务先读 [视觉规范](../../../DESIGN.md)，权限任务参考 [权限矩阵](../../../docs/ACL-MATRIX.md)。修改代码前查看 [经验记录](../../../LESSONS.md) 的相关条目。
- 是否提 Issue 由用户决定，不按改动大小自动要求建单。要求提 Issue 就调查并发布，不再先出草稿等待确认；要求实现或修复就直接开发。用户明确限定为草稿、规划或只读时，遵守该范围。
- 默认从当前仓库的 Git remote 确认 GitHub 目标，不凭历史记忆向其他仓库写入。优先使用可用的 GitHub 连接工具；能力不足时使用已认证的 CLI。写操作失败后先检查远端状态，避免重复创建。
- 提 Issue 不包含实施授权，开发不自动包含合并或发布授权。按本次请求及已有明确授权执行，不反复确认已授权的动作，也不扩大范围。
- 默认不启动其他 Agent。用户安排其他 Agent 开发时提供可独立接手的记录；需要委派时遵守当前环境和用户的授权。

## 从目的到可交接任务

先将想法收敛为：谁在什么场景遇到什么问题、完成后能观察到什么结果、本轮做到哪里。能从代码和现有记录查明的事实自行调查；只有影响目标或重要取舍且无法查明的问题才询问用户。

尚不明确的交互或视觉方向，可以先通过小原型验证选择；不把原型未经验证的结论当作正式需求。复述目标保持简短，不为常规实现选择等待审批。

用户要求发布 Issue 时：

1. 搜索已有 Issue 和相关 PR，阅读候选项的完整讨论及最新变更，避免重复任务或执行已撤回的需求。已有同一问题时，在授权范围内补充记录。
2. 写清目的、当前行为与复现证据、本轮范围、用户可观察的验收条件、相关模块和交付证据。区分事实、假设和实现建议，不把建议写成没有依据的硬约束。
3. 发布后返回链接。附件只有成功上传或已有可访问地址时才引用；本地路径不能冒充 GitHub 附件，缺失时说明。

Issue 或任务记录应当让新 Agent 无需完整聊天历史也能接手。拆分大型任务时，每一部分都应结束在可验证的状态，并写明依赖；不默认拆成只有技术层完成、用户仍无法体验的任务。

## 实现与可信验证

### 让正确实现成为默认选择

- 代码库是后续实现的范例。先找已有的正确模式，避免继续复制补丁和过时接口。
- 缺陷先在报告者实际使用的入口与条件下复现，再追到首次出错的位置。搜索相邻分支、调用方和同类实现，修复同一根因覆盖的案例，避免无关扩张。
- 反复纠正同类问题时，依次考虑：用接口、数据结构或状态模型消除错误选择；用类型、静态检查或自动测试拒绝错误；最后才补充需要判断的文字规则。
- 不机械禁止注释、某个 API 或既有框架，不为表现严谨引入无关抽象、形式化证明或更多 Agent。具体约束必须服务于已确认的问题。

### 用证据说明结果

遵循工程协作指南的验证门槛，根据改动选择相关的补充检查。命令及环境以当前 Makefile、package.json 和工作流为准；不把提交 PR 当成 CI 已运行。

| 改动类型 | 需要验证的实际行为 | 当前可复用入口 |
| --- | --- | --- |
| Web / PWA / Electron 界面 | 在真实页面操作目标路径及相关异常状态，检查适用的桌面、移动端和明暗主题，保留前后截图；涉及桌面专属行为时验证 Electron | `npm --prefix web run test:e2e`、相关前端测试、`npm run desktop:typecheck` |
| Backend / Runner / Session | 从请求到实际执行、持久状态和结果投递，覆盖本次涉及的失败、取消、重试或恢复 | `npm test -- --run`、`npm run self-test:agent-runner` |
| 权限、工作区及用户隔离 | 允许场景与拒绝场景，检查真实路由和资源归属，避免只测内部函数 | 对应 ACL、路由和隔离测试 |
| Cloud Runtime / Authority | 涉及的 Worker 行为与 Node authority 集成链路 | `npm --prefix apps/cloud-agent test`、`npm run test:cloud-authority` |
| 真实模型、渠道或外部服务 | 在对应环境验证实际链路；缺少凭据或环境时明确哪些行为没有验证 | 对应 live / smoke 脚本，如 `npm run test:real-model` |
| 性能 | 相同条件下记录改前、改后测量，排除未执行实际工作、缓存或错误率变化造成的假改善 | 当前功能的测量脚本、trace 或性能工具 |

- Bug 有合适的本地测试路径时，先保留能复现行为的失败测试，再修复；撤销修复后测试应因目标行为失败，编译错误或跳过不算。普通视觉微调不为凑数量添加与实现同构的测试。
- 编译、Mock 测试、真实系统验证分别报告。截图不能代替状态转换验证，Mock 不能证明真实模型或渠道可用。
- 使用隔离的测试数据和临时目录，不覆盖日常运行配置、数据库或凭据。证据中不包含秘密信息。
- 检查失败时判断是本次回归、既有缺陷还是环境问题。不得通过削弱断言、提高阈值或反复重跑直到通过来掩盖失败；记录可复现原因和对交付的影响。
- 连续修补没有改变失败结果时，回到根因或前提验证，不无限重复同一方案。缺少必要环境、权限或产品决定时，说明具体阻碍与可继续的部分。

## 交付与独立验收

开发者对实现和自测负责。用户安排独立验收时，验收者按目标重新检查，不直接采信开发者的通过声明。

- 交接或 PR 说明包含：用户行为如何变化、关联任务及范围、验证命令和结果、运行证据、未验证项和已知限制。写明对应提交 SHA；未提交的本地结果注明基准提交及未提交改动。
- 验收先读需求及最新讨论，确认实际代码版本，再检查完整用户路径、相关边界和异常情况。复用已有证据，但对关键行为独立复现；有价值时尝试撤销修复或构造反例，证明检查能捕获错误。
- 只提交有证据的缺陷，说明触发条件、影响与修复方向。明确结论：通过、需修复或证据不足。仅完成自测时，写明“尚未独立验收”。
- 审查后提交发生变化，重新检查受影响内容和必要门槛；合并前确认实际待合并版本与验收版本一致，不能沿用已失效的结果。
- 问题属于实现缺陷时交回修复；属于目标变化时更新任务记录，让实现重新对齐。通过验收不自动执行未授权的合并、发布或用户回复。
- 获得发布授权后，还需确认目标版本的构建及产物实际可用。创建 tag、发起 workflow 或提交部署请求不等于发布完成。

## 反馈维护与经验沉淀

在用户指定的反馈来源、任务范围和时间边界内处理维护，不默认开启全天监听、社交平台回复或无人值守发布。一次维护批次以处理完约定范围、达到约定预算或遇到必须由用户决定的阻碍为结束点。

1. 汇总反馈，按版本、平台、症状与复现路径去重，确认是否值得做及是否已有负责人。同一任务由一个开发负责人推进。
2. 并行开发经授权时隔离工作目录；不得在同一 checkout 中相互覆盖或提交他人的改动。同一机器避免并发完整测试套件造成资源争抢，相关测试按需执行。
3. 只对实际发生、且会改变后续做法的返工或遗漏复盘，写入 [LESSONS.md](../../../LESSONS.md)。不为每次成功任务强行制造教训。
4. 每条经验包含问题、原因、Issue / PR / 提交或验证证据、预防措施、适用范围、观察日期和实施状态。同日重复运行只算一次观察；合并相同根因条目。
5. 同一教训在三个不同日期出现时，复核是否升级为长期工程约束。严重或清晰的问题首次出现即可处理；计数不是延迟修复的理由。
6. 优先将教训落实为接口、类型、检查或回归测试。已落实的经验指向其约束位置，过时的经验移除或标记失效，避免累积越来越长的口头禁令。

复盘发现的改进在当前授权范围内落实；超出范围时记录待处理项，不借复盘进行无边界重构。完成任务时简要说明结果、验证和剩余限制，不把操作流水账作为交付。
